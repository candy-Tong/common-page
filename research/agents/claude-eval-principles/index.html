Hillclimb 不是“模型自我训练”，
而是有护栏的局部搜索。

它先把“好不好”变成可以重复测量的函数，然后只允许在一个可控表面上改一件事，观察分数变化，再决定保留还是回滚。真正的难点不是生成补丁，而是确保这个分数值得相信。 [S1]

01 / MEASUREMENT FUNCTION

第一层原理：Eval 是“测量函数”

你并不是直接优化“智能”。你先定义一套任务分布与评分函数，把一个复杂应用压缩成可以比较的观测值。这个压缩越失真，后面的自动优化越危险。

原理抽象

从现实目标到一个数字，中间有 4 次压缩

  1. 现实任务 → 样例：样例必须像你真正关心的生产任务。
  2. 行为 → 轨迹：要保留模型、工具调用、最终状态与消耗。
  3. 轨迹 → 分数：程序检查、LLM judge 或人工判断都可能引入误差。
  4. 很多分数 → headline：均值可能藏住某类严重回归。
所以 build-eval 的核心不是“生成 50 道题”，而是不断问：这把尺子是否真的测到了我要上线的结果？ [S2]
02 / WHEN THE RULER IS CLIMBABLE

第二层原理：好的 Eval 要有“可爬的坡”

原文给出四个特征：任务像生产、更强模型通常更好、顶部仍留有可通过的提升空间、运行波动要小。它们共同决定这张地图是不是一张能用的“地形图”。 [S1]

原文原则
01分布像生产否则你只是优化 benchmark 的趣味题，不是上线表现。
02能力顺序合理更强模型 / 更高 effort 通常应更好；反常可能提示题目或 grader 有问题。
03有 headroom若已接近满分，质量方向没有足够坡度；更适合改成本或延迟。
04低方差同一配置反复跑却上下乱跳，候选之间的小差异就无法归因。
03 / LOCAL SEARCH LANDSCAPE

第三层原理：Hillclimb 是局部搜索，不是全局求解

把系统配置 θ 想成地形上的一个位置。每轮补丁只是从当前位置走到附近一个候选点。它能稳定找到“附近更好”的方向，但没有数学保证找到全局最优。

04 / ONE ROUND AS A STATE MACHINE

第四层原理：一轮 Hillclimb 是“假设检验状态机”

官方流程的纪律在于：分析器只读 train 侧失败 → 提一个可归因修改 → 用固定口径重跑 → 看 test 与护栏 → 保留或回滚。不是看到低分就不停改到它变高。 [S3]

05 / WHY A HELD-OUT SPLIT EXISTS

第五层原理：过拟合发生在“搜索器”与评估集之间

只要你反复观察一组题的反馈，并据此选择版本，这组题就在向搜索过程泄露信息。把具体失败内容隔离到 train，把未见样例留作 test，可以发现“只是学会了这几题”的候选。 [S1] [S3]

机制解释

①
分析器只读 train 轨迹
阻止它直接把 test 的具体失败抄进 prompt。
②
答案结构性隔离
不是写一句“不要偷看答案”，而是让答案根本不可访问。
③
更严格发布：validation 选版本，final test 最后一次验收
因为每轮拿 test 分选优，也会逐步消耗 test 的独立性。
06 / SIGNAL VS NOISE

第六层原理：只有“高于噪声”的改动才值得花一轮

当模型输出具有随机性时，分数变化 = 真正效果 + 采样波动 + grader / 环境波动。官方 hillclimb 会在开始前比较噪声下限、可提升空间和你真正会采取行动的最小改进。 [S3]

07 / WHAT THE ALGORITHM CANNOT GUARANTEE

边界：为什么它有效，但不是“自动得到最优 Prompt”

原理上，它依赖的不是神奇搜索算法，而是三件事：局部修改便宜、测量信号可信、每次修改能被归因。任意一条失效，hillclimb 都会退化成“自动试错”。

结论
A

没有全局最优保证

Prompt、模型、工具和 harness 构成高维离散空间。逐步爬坡可能卡在局部高点，也可能需要先走一步“暂时变差”的路线才能到更好的区域。

B

不能替代产品分布验证

Eval 永远是现实任务分布的近似。benchmark 上升只是证据链的一环，最终仍需在新的、未用于选优的数据与真实约束下验收。

C

修改面越大，归因越差

改一句 Skill 描述通常便宜、易回滚；开放式重构 Agent harness 可能同时改变几十个变量，分数变了也很难知道为什么。 [S1]

一句话模型：Eval 提供“坡度”，Analyzer 提供“往哪走的假设”，Patch 是“一小步”，Held-out split 是“防止只记住路标”，Noise gate 决定“这一步是不是大到足以相信”。
TRAIN

可以读具体失败，用来生成候选。

VALIDATION / TEST

用来判断候选是否泛化；不要把具体失败内容反馈给分析器。

FINAL TEST

更严格发布时最后一次使用，避免反复选优耗尽独立性。
