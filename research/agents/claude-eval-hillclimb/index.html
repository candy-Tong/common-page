自动优化之前，
先让分数可信。

不是让模型自己训练自己，而是让 Claude 帮你建立评估，再反复修改应用、对照结果。真正难的不是“自动改”，而是知道哪次修改真的有用。[S1][S3]

01 / WHAT IS BEING OPTIMIZED

它到底优化哪一层？

是一位会做对照实验的应用开发助手，不是一次新的模型训练。

概念定位

调的是模型周围的应用

Claude Code 读取工作流、项目和评估结果，提出修改并执行。优化器可以选模型、改指令、调参数或改外围代码，但不会在这个流程里更新基础模型权重。[S3]

train 在这里主要表示“优化器可以查看的开发样本”，不是送去做梯度下降的训练集。分析修改的模型和被测试的模型，也可以不是同一个。[S3]

系统提示词、Skill / 指令文件可修改
工具描述、调用方式可修改
模型选择、effort、API 参数可修改
Agent 外围代码与执行流程约定范围后修改
基础模型权重、预训练过程不在此流程内
本页判断：价值在于把零散的“试个 Prompt”变成能追查原因、能回滚的实验。一次局部修改失败，不代表组合修改无效；自动爬坡也不保证找到全局最优。

先造尺子，再用它迭代

build-eval 定义怎么测，hillclimb 在已认可的测量方式下尝试改进。

01 / SCOPE

锁定一个真实任务

找到实际应用入口，明确输入、输出和成功条件；现有运行器与案例优先复用。[S2]

02 / INPUTS

样本像真实使用

优先可保留的生产记录、工单与真实种子；覆盖正例、反例和混合意图，人审过再继续。[S2]

03 / GRADER

明确怎样才算做好

固定标签用代码检查；开放回答用可检查的标准。操作型 Agent 优先检查最终状态。[S2][S6]

04 / BASELINE

排除错误，保留基线

同一次调用保留输出、评分和消耗。核对噪声、可提升空间与环境，再开始优化。[S3]

/claude-api hillclimb

读失败 → 提补丁 → 测 → 取舍

先约定目标、可改范围、预算与停止条件。分析器只读训练侧轨迹，每轮围绕一个失效原因提修改，保留补丁和结果。有回归或收益不清楚，就不能只凭一次高分合并。[S3]

WORKFLOW ≠ TURNKEY PRODUCT

不是“装完就能测任何应用”

官方提供运行器骨架与报告工具，但仍需接入 loadCases / runCase / gradeCase：怎样加载你的样本、调用你的应用、评判你的输出。[S4]

文章与核查版本的差别：原文介绍输入审阅页；当前仓库更偏向 Markdown 或既有报告工具，并提醒不要把未经信任的日志直接拼进自写 HTML。界面只是载体，人工确认与内容转义才是关键。[S1][S2]

EVIDENCE BOUNDARY / 本页判断
支持“可以尝试”，不支持“普遍保证”
提示词、模型、思考力度和评分方式都可能变化。要识别各自贡献，需要统一口径的基线重评和消融对照；要判断上线收益，还需要真实任务分布上的验证。
单请求便宜了，整体就一定省钱吗？
不一定。优化过程还要花费候选评估、分析器、评分模型、失败重试与工程成本。粗略回本量 = 优化总投入 ÷ 每请求节省额；两者必须采用同一成本口径。原文的 token 成本不等于端到端总成本。

06 / READ THE FINE PRINT
最需警惕的，不是“自动化不够”
而是自动化把错误尺子、小样本和反复选优的偏差一起放大。
方法审计
01
每轮选优，就不再完全独立
默认流程不把测试轨迹交给分析器，却会利用每轮测试分选版本。它降低直接记答案的风险，但不能完全排除选择偏差。[S3][S7]
02
重复同一道题，不等于覆盖新场景
重复试验测模型随机性，不能弥补任务覆盖不足。若反复使用同一个随机构建的检索库，还可能漏掉构建本身的波动。[S3]
03
评分变了，前后数字需要重算
修坏题和错误评分是必要工作。但必须用新口径重评基线与候选，才能区分应用改进和原来扣错分。[S3]
04
流程隔离，不等于安全隔离
只传训练轨迹是工作流约束。若模型仍能读到答案文件，就没有强边界；运行器的哈希检查也不能代替权限控制和沙箱。[S3][S4]
需要对外宣布效果时，把最后一份数据留到最后
TRAIN读失败 · 提修改
优化器可以看
VALIDATION每轮比较 · 选版本
用于开发决策
FINAL TEST冻结方案后验收
不再据此选新版本
官方默认采用 train/test，也允许较大样本时加第三份切分。本页把“最终测试只用一次”作为更严格建议，不把它误写成默认实现。数据不足时，结果应标为方向性信号，不要硬切出三份都测不准的小集合。[S3][S7]
噪声直觉计算器
简化独立试验模型 · 非显著性检验
假定各次尝试独立、成功概率相同。真实任务中的重复往往相关，这个近似可能过于乐观；低样本或接近边界时也不可靠。
单个成功率的近似 95% 区间半宽
半宽 ≈ 1.96 × √[p(1−p)/(n×r)]
这不是候选减基线的区间。正式比较应采用逐样例配对差值，按任务聚合或重采样，并处理多轮选优和环境变化。


07 / FROM READING TO IMPLEMENTATION
落到项目里，先收紧目标
不要从“把整个 Agent 变好”开始。先挑一个能复现、看得懂、改得起的环节。
实践建议
给 build-eval 的任务说明
/claude-api build-eval

只评估邮件进入哪个处理队列。
先检查已有入口与测试，不替换已有框架。
输出仅为 billing / security / support。
覆盖单一意图、混合意图与不触发的反例。
不要使用未脱敏生产数据。
先让我确认样本、评分规则与预算，
再调用模型。记录完整结果与重试消耗。
给 hillclimb 的任务说明
/claude-api hillclimb

目标：降低单请求成本，保持质量。
先约定质量容忍幅度、预算与停止条件。
只改 routing.md 和模型 / effort 配置。
不改测试标签、评分器和安全策略。
每轮一个失效原因，保存 diff 与记录。
样本足够时划 train / validation / final test；
用 validation 选优，最后验收 final test。
MINIMUM PAPER TRAIL
至少留下这些证据
eval-flow/                 缩略示意
├─ _state.json             目标 / 切分 / 版本
├─ baseline/               未修改的起点
│  ├─ results.jsonl        逐例逐次成绩
│  └─ traces/              对应调用轨迹
├─ v1/
│  ├─ change.md + .patch   改什么 / 为什么
│  ├─ results.jsonl        本轮结果
│  ├─ errors.jsonl         重试 / 基础设施错误
│  └─ traces/              本轮调用轨迹
└─ report.html             人工审阅入口
输出、评分、模型标识与调用消耗要对应同一次执行。不要重新调用一次模型来补轨迹，却仍使用上一次的分数。[S3][S4]
MEASUREMENT BEFORE MERGE
合并前，回答三个问题
① 提升来自应用，还是来自测量方式变化？
② 收益超过波动，关键反例也没有变坏吗？
③ 换一批任务与真实环境，这个改动还有效吗？
“没有找到可靠改进”也是有效结果。及时停止一次测不准的试验，比再加几句指令更有价值。
