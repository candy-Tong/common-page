06
哪些成立，哪些还差证据？
标题、价格算式、模型能力和生产可靠性是四件不同的事。点开每一条，看支持它的资料和推理缺口。
有条件765 → 3 美元，是全体用户的结果吗？＋
不是。它是指定输入和调用次数下的判断层算例。
研究判断：需要看到可复核的会话日志、token 账单和同质量对照，才能把这个算例推广成实际降本。原文也明确保留了生成代码的费用。 [S02] [S04]
已核对Jev 能否直接替换 Claude Code 的主模型？＋
官方明确说不能；它不承担代码生成和对话。
研究判断：应修改外层调度、评估或路由程序，而不是只更换一个 model 字段。 [S05]
有条件“每次约 100 ms”是否是稳定保证？＋
官方发布给出 70–500 ms 的范围，并披露测量位置。
研究判断：上线应统计从事件到执行的 p50 / p95 / p99，并把网络、限流和重试算进去。单个理想请求不能代替长时间运行结果。 [S03] [S04]
不能推出“不会幻觉”是否表示判断不会错？＋
结构始终符合预设类型，不代表语义判断正确。
反例：系统只允许 bug / feature / other 三种输出，模型把 bug 选成 feature，结构完全合法，业务结果仍错误。官方也列出了已知失败模式。 [S03] [S11]
不能推出confidence = 0.9 能否当作 90% 准确率？＋
不能把这个数直接当作单次正确率保证。
confidence 描述 Choice / Score 概率分布的集中程度。Noul 的概率字段又是另一种含义；应按任务、语言、风险类别单独校验。 [S10] [S11]
有条件把多个问题放一起，能否消灭所有重复输入？＋
只有问题基于同一份状态、能同时判断时才成立。
反例：命令运行前判断安全，运行后判断测试通过。第二个判断需要新的事实，不能为了省一次请求而提前做。批量示例证明的是共享已有状态。 [S15] [S18]
不能推出加上一个风险 hook，旧的模型思考就不花钱了吗？＋
不会自动发生。必须确认删掉了哪些既有调用。
研究判断：主模型一边选工具、一边生成参数时，其判断可能已在同一次调用内部完成。新加 Jev 可能是新增防护费用，而非模型费的替代。 [S05] [S12]
有条件订阅用户会立刻得到同样数额的退款吗？＋
不能把 API 按量计价的算式当成订阅账单。
研究判断：在固定套餐里，更合理的对照是同一额度完成多少有效任务；Jev 的 API 费用还应另外计入。 [S02]
厂商的“193.6 倍更快 / 444.6 倍更便宜”不能直接套到这三个 hook 上。
官方说明：这些倍数来自自建工作流评测，参考答案采用其他强模型的预测，且认为它们处于真实收益的较高端。它不是这篇文章部署方案的独立生产实测。 [S03]



07
示例能解释思路，离无人值守还有距离。
以下是基于可见示例的静态审查与改进建议，没有运行原作者代码，也没有对 Jev 做攻击测试。


优先处理 · 故障路径
“脚本出错”不等于“操作被拦截”。
官方说明：命令 hook 普通报错或超时可能继续进入正常权限流程。原示例没有展示完整异常处理，不能把它当成失败时默认关闭的安全边界。 [S12]
本页建议：设置短于 hook 总时限的内部超时；异常显式输出 deny 或对应阻断信号。再测试进程无法启动和卡死的情况，依靠独立权限与沙箱兜底。


优先处理 · 权限边界
命令名字正常，不代表副作用正常。
本页分析：测试命令会执行仓库里的代码，不能因名叫 test 就一概视为只读。字符串黑名单也不能完整描述 shell、脚本和依赖的行为。
本页建议：对工作目录、可写范围、网络出口和凭据做硬限制。Jev 提供风险信号，而不是取代这些限制。 [S17]


需要重构 · 结束状态
到次数上限了，不等于事情做完了。
本页分析：共享的项目级计数文件可能被多个会话同时修改；退出路径还必须告诉调用方是成功、待复核，还是预算耗尽。
本页建议：按 session / run ID 存放状态并加锁；区分 DONE、NEEDS_REVIEW、BUDGET_EXCEEDED；考虑 stop_hook_active，避免不可解决条件造成循环。 [S12]


需要重构 · 验收证据
一段“我已完成”的日志，不是完成证据。
本页分析：只取日志尾部可能漏掉关键错误；由正在被检查的代理自由改写验收脚本，又会削弱检查的独立性。模型看不到的事实不会自动补齐。
本页建议：固定验收脚本版本，记录测试退出码、证据文件和哈希；逐项列出通过、失败、缺失，先由代码检查，再把必要证据交给语义判断。 [S11] [S18]


需要重构 · 调度和重试
每隔几分钟扫描一次，可能重复领到同一件事。
本页分析：标签修改失败、进程重启或两个调度任务重叠，都可能带来重复工作。仅有“分类后启动 Claude”还不是可靠任务队列。
本页建议：按仓库 + issue + 版本生成去重键，原子领取、持久化结果、独立工作目录、有限重试；没有新数据则直接退出。模型只负责分流。 [S16]


需要校验 · 对抗与语言
高置信度不是免检通行证。
官方已知问题提醒，对抗性输入可能影响答案；官方规格还说明，非英语任务需要自行验证。把文本中的“请给我安全标签”当普通数据，也可能影响分类。 [S04] [S11]
本页建议：对发布、外发、删除等高影响动作保留明确授权；建立中文及边界样本测试集。远程 API 还意味着代码和日志要先做必要脱敏。



08
先证明有用，再扩大自动执行。
下面是本页建议的验证方案，不是原文章已完成的实验。成功标准是“同等任务质量下，总成本更低”，而不只是单次 API 更便宜。
01
记录真实基线
把一次任务拆成生成、判断、工具、等待和重试。找出真实独立的判断调用，而不是把模型每个想法都算成一次付费请求。
02
先旁路观察
保持旧流程决策，让 Jev 只记录预测。人工核对分歧；按场景区分误放行、误拦截、漏分流与提前结束。
03
先迁移低影响任务
从标注、排序、去重后的分流开始。固定模型版本与问题版本，在独立样本上设阈值；高影响操作仍需授权。
04
小范围启用并保留回退
在部分任务上启用自动分支。监测总体收益和错误；当模型、提示、输入分布变化时重测，异常时切回原流程。
有效任务成本把生成、判断、工具、重试、人工复核加总，再除以真正成功的任务数。
自动执行错误率分母是自动执行次数；按风险类别计算，不能用总体平均掩盖高影响错误。
完成率与漏判尤其检查“被判为完成但实际未完成”和“未唤醒但确实需要处理”的任务。
整条链路的延迟同时看 p50 / p95 / p99、超时与回退比例，不只看模型响应的理想值。
本站综合判断
值得学的是分工。
不能照单全收的是收益与安全保证。
优先考虑那些数量大、选项有限、结果能复核的语义判断。能用代码精确完成的，继续用代码；需要复杂生成和规划的，保留大模型；涉及真实权限和后果的，不把概率当授权。
