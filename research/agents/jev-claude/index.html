01 / 主帖主线 · [A]

它讲的不是模型介绍，而是一套任务处理流程。

下面每张卡先标出主帖对应的动作，再解释它在程序里应落到哪里。实现解释是本页分析；不是主帖已经提供了一套可直接部署的“企业大脑”源码。

图为本页重绘；手机可横向查看。缓存与筛选由应用组织，不能理解为 Jev 自动操作 Claude 的内部缓存。

01 · 划清三个角色

生成、判断、执行分开。

主帖把复杂思考交给 Opus，把有限选项判断交给 Jev，把最终分支交给代码。落地时要把模型调用放进已有应用，而不是让两个聊天机器人互相商量。[A]

02 · 改写问题的输出契约

问一个字段，而非要一段解释。

例如工单返回类别、严重程度、是否有复现步骤。代码消费 Choice、Score、Noul 的字段，不再从长篇自然语言里猜“是否同意”。[C]

03 · 共用一次状态输入

类别和条件题一起问。

先问工单类别，再问是否退款，会多一次往返。并行提出两类问题，拿到类别后只用相关答案；账单问题的“缺陷严重程度”应被丢弃。[D]

04 · 分支由应用代码决定

简单请求不必叫醒大模型。

把判断值、业务规则和复核阈值组合起来，走模板、标签、队列等已有流程。“约 99% 在这里结束”是主帖主张，不是任意企业都已验证的比例。[A]

05 · 路由要连同上下文成本算

便宜模型不一定让整段会话更便宜。

主帖用来回切模型的 5.84 与保持同一模型的 3.32 作比较。这里保留原主张，但未取得其完整工作负载，不能独立复算；选型需要连缓存写入、重读和输出一起比较。[A]

06 · 稳定上下文重复使用

固定前缀，变化内容放后面。

把稳定的规则、工具和背景作为可复用前缀，把当前事件放在后面。缓存命中不是“永远记住”，仍受前缀匹配、有效期和模型等条件影响。[E]

07 · 只升级真正困难的部分

把问题连同证据交给 Claude。

常规问题只需现成处理程序；需要诊断、规划或写补丁时，再交给大模型。本页解释：升级包应包含原始事件、相关资料、约束及已经做过的检查，而不只是一个“bug”标签。[A]

08 · 每轮按当前问题挑上下文

原样保留、交给生成模型摘要，或删除。

Jev 负责判断片段价值，应用重组动态上下文；Jev 本身不负责写摘要。本页建议保留稳定前缀，把动态筛选放在后缀，避免每轮改写前部导致缓存失效。[A] [G]

09 · 在命令执行点拦截

审的是实际 Bash 命令，不是计划。

Claude 提出工具调用后，PreToolUse 收到本次参数；先跑硬规则，再判断，再返回 allow / deny / ask。这个位置与给模型写一句“请小心”不同。[F]

10 · 复核每次运行记录

把结果检查接到运行结束之后。

为每条 trace 配置明确评价题，保存结果并将失败项送人工复查。主帖按每次 $0.00035 估算 10,000 条为 $3.50，并报告某组 500 个判断与人一致；这是特定报告，不是长期零错误保证。[A]

原文档中的条件是：缺陷再检查严重程度与复现情况；账单再检查退款；需求进入需求记录；客户情绪可对各分支追加优先回复标记。本页另外添加了低确定性复核出口。
# 逻辑说明，不是完整可部署服务
if uncertain(category):
    send_to_human()
elif category == "bug_report":
    engineering_queue() if severity > 1.5 and repro > .6 else bug_backlog()
elif category == "billing":
    billing_queue(refund_flag=refund > .7)  # 标记不等于执行退款
elif category == "feature_request":
    feature_backlog()
if frustration > 1.5:
    flag_priority_reply()
这里真正节省的是什么？五题共用同一份工单，不是五次重发；不相关答案只被忽略，不被当成执行依据。问“是否要求退款”和“是否有权退款”是两回事。

三个机制不能混为一谈：路由决定是否、以及由谁处理；缓存减少重复前缀处理；筛选决定这轮实际发送什么。缓存价低，不代表无关内容应该一直留下；每轮筛选也不意味着稳定前缀必须被重写。


04 / 被引用文章 [B] 的三个接入案例
不是“安全、验收、分流”三个名词，而是三个程序入口。
以下按原文章脚本拆解接口、数据来源和分支，不逐字转载完整代码。配置是本页重写；输入输出是用于解释原分支的样例。生产加固建议独立标注，不能当成原作者已经实现。


原文章 Build One
案例一：每条 Bash 命令执行前，先过审批脚本。
原场景：Claude Code 运行长任务，工具会不断提出实际命令。接入点：PreToolUse 匹配 Bash，从标准输入读本次工具 JSON。[B] [F]
Claude 提出 Bash → hook 读 command / cwd → 代码硬规则 → Jev 风险类别 → hook 返回执行决定
传给谁、传什么
event.tool_input.command
        + event.cwd
             ↓
state = {command, cwd}
question = 风险分类 Choice
             ↓
choice + confidence
原脚本分支（不是本页重设的规则）
命中硬拦截字符串deny，不调用 Jev
read_only / local_edit 且 confidence ≥ 0.9allow
destructive 且 confidence ≥ 0.9deny
external、other 或不确定ask
看配置与一次完整输入输出
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/jev_gate.py\""
      }]
    }]
  }
}
上面是 POSIX shell 写法，实际要替换为安装 SDK 的 Python；不是 Windows 通用命令。
输入：{"tool_name":"Bash","tool_input":{"command":"git diff --stat"},"cwd":"/work/project"}
Jev 摘录（模拟）：{"choice":"read_only","confidence":0.97}
输出：{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","permissionDecisionReason":"已按本次命令分类"}}

改成 git push：即便 external 的 confidence 很高，原脚本也走 ask。
改成 other：仍走 ask，不会因为确定地“不知道”而放行。
本页加固建议：字符串匹配不是完整安全隔离；测试也可能写盘或联网，不能一律叫“只读”。异常、超时、权限和工作目录必须单独处理。原文章还提到 LangChain 的 AutoModeMiddleware；这里不声称已运行或验证其安装配置。

原文章 Build Three
案例三：先在定时脚本里筛工单，确实要改代码才启动 Claude。
原场景：定时调用完整编码会话检查 issue，即使没新事也消耗一轮。接入点：外部 cron 运行 triage.py，而不是在 Claude 内部不断询问。[B]
cron → gh 取 new 标签工单 → Jev 分类 → 改标签 → 仅 code_fix 启动 claude -p → 复现、测试、补丁、草稿 PR
原脚本保留了哪些实际操作
调度：每 10 分钟
读取：最多 30 条，标签 new
字段：number / title / body
分类：code_fix / question / junk / feature / other
确定性门槛：confidence ≥ 0.9 且不是 other
改标签：移除 new，添加分类或 needs-human
启动：仅 code_fix → Claude
会话任务：复现 → 失败测试 → 修复 → 草稿 PR
同一次轮询里，三张工单走不同出口
本页样例输入结果（模拟）
日期导出错误，附重现步骤code_fix → 编码会话
如何导出 CSV？question → 贴标签，不启动编码
能加暗色主题吗？feature → 等待需求处理
没有新工单普通代码退出，两种模型都不用调用
看接口边界与新增可靠性条件
gh issue list --label new --json number,title,body --limit 30
    ↓ 每条工单作为 state.issue
Jev Choice：这条工单需要维护者做什么？
    ↓ confidence 不够或 other → needs-human
gh issue edit <number> --remove-label new --add-label <分类>
    ↓ 仅 code_fix
claude -p --permission-mode acceptEdits <复现、测试、修复、开草稿 PR 的任务>
这是原脚本调用顺序的重述，不是可直接复制的整套服务。命令里的尖括号需替换。启动会话还要加载前两个 hook；不是外层分类过一次，后面所有命令就都获得批准。
本页加固建议：先检查是否已有同一任务在运行；使用工单号和版本去重、加锁，检查 gh 的退出码。原脚本“先移除 new 再启动”还需失败恢复，否则启动失败的工单可能不再被捞起。
